# 规格：中断恢复第 3 批——启动清理、上限与回收

## 背景与目标
2026-11-03 的盘点还查出一批低严重度问题：中断后留下的文件不会被清理，有些数据会无限增长。单看每一项都无害，但会日积月累地占用磁盘、在资料库里留下杂物，个别还会导致迁移不完整。

本批在启动时统一清理一次、给会增长的数据设上限、回收已经没人引用的缓存。前提是第 1、2 批已经合入。

## 非目标
- 不改第 1、2 批已经修过的逻辑。
- 不删除任何用户文档。
- 不新增依赖。

## 设计
1. **启动清理**（新增 `server/startupSweep.js`，后端启动后延迟 30 秒执行，异步且低优先级，不阻塞启动和扫描）：
   - **数据目录**（`dataDir()` 下递归，跳过 `models/` 内部）：
     - 删除修改时间超过 1 小时的 `*.tmp-*` 文件，以及 `cache/convert-*` 目录。
     - 删除 skill 安装留下的 `skills/.*.tmp-*` 目录。
   - **资料库目录**（每个已打开的库）：
     - 删除修改时间超过 1 小时、且符合本应用命名规则的临时文件：`*.wb-tmp-*`、`*.wb-copy-*`、`*.wb-case-*`。
     - 只匹配这几种命名，一律不碰其他文件。
   - **RAG 模型目录**：只删除另一种后端（onnx/mlx）残留的 `.part`，并且只在当前没有下载进行时才删。
   - **限制条件**：清理期间每处理 50 个条目让出一次事件循环。删了哪些文件汇总记一行 INFO；单个文件删除失败只记 WARN，不中断清理。
2. **`.bak` 备份上限**（`knowledge/<dsId>/backups/`）：
   - 每个文档最多保留最近 20 份备份。
   - 每个库的备份总量超过 500MB 时，按时间从最旧的开始删，直到降到 500MB 以下。
   - 在启动清理时执行，保存时不检查。
3. **`incidents.jsonl` 上限**：超过 1MB 时，只保留最近 500 条。在启动清理时执行，写入方式为原子写。
4. **Word 缓存回收**：每次扫描、建完索引之后，删除当前快照里已经不存在的文档所对应的 `word-*.json` 和 `word-assets/<key>-*` 目录。
   - 缓存键由 `relPath` 计算出来，回收时用同一套算法从快照反推，不能另写一套。
   - 只在这次扫描成功完成后执行；扫描失败或扫描被取代时不回收。
5. **资料库内的 `.trash` 中转**：如果有批次目录在启动时仍然停在 `<库>/.trash/`（上次在交给系统回收站之前就中断了），就重新尝试把它交给系统回收站。成功后删除中转目录；失败时保留，并记 WARN。
6. **数据迁移的几个边界**（`server/store.js`、`server/agent/manager.js`）：
   - **旧版数据迁移**：把 `config.json` 放在最后一项迁移，确保其他条目都迁完了才迁它。如果再次启动时发现旧目录里还有条目、但 `config.json` 已经不在，就继续迁完剩下的条目，并写上 `MIGRATED.txt`。
   - **`sources` 迁到 `knowledge`**：目标目录已经存在时，把源目录里目标缺少的条目逐项合并过去，不再整体跳过。
   - **`migrateIfNeeded` 的日志**：失败时日志写成实际行为，例如「改名失败，继续使用新位置」，不要写成「继续使用旧位置」这种和实际相反的话。
   - **助手 skills 迁移**：新目录不为空时，把旧目录里有、新目录里没有的 skill 逐个补齐。

## 边界情况
| 情况 | 期望 |
|---|---|
| 一个临时文件刚创建不到 1 小时 | 不删除（它可能正在被使用） |
| 库内有用户自己创建、名字形如 `foo.tmp-1.md` 的文件 | 不删除（不符合本应用的命名规则） |
| 多个库共用一个父目录 | 每个库只清理自己目录下的文件 |
| 清理过程中有新的保存操作 | 新保存产生的临时文件不到 1 小时，不受影响 |
| 回收系统回收站中转时失败 | 保留中转目录，记 WARN |

## 验收标准
- **G1**：`npx tsc -b`、`npx eslint .` 结果均为 0 问题，`npm run build` 成功。
- **G2**：新增 `scripts/test-startup-sweep.mjs`，在临时数据目录和临时资料库中预置以下各类文件，修改时间通过 `utimes` 设置：
  - 超过 1 小时的 `.tmp-*`、`.wb-tmp-*`、`convert-*`、`skills/.x.tmp-*`
  - 不到 1 小时的同类文件
  - 用户文件 `foo.tmp-1.md`
  - 某一篇文档的 25 份 `.bak`
  - 超大的 `incidents.jsonl`
  - 已删除文档对应的 Word 缓存和图片目录
  - 停在 `.trash` 里的批次目录（系统回收站用桩模拟）

  运行启动清理和一次扫描加建索引之后，逐项断言：
  - 该删的都删了；
  - 不该删的都在，包括用户文件和不到 1 小时的临时文件；
  - 每篇文档的备份剩 20 份；
  - `incidents.jsonl` 剩 500 条；
  - 仍然存在的文档，其 Word 缓存都还在；
  - `.trash` 里的批次目录已经交给系统回收站并被删除。
- **G3**：在 `scripts/test-security.mjs` 或新增测试中，覆盖第 6 条的三个迁移边界：中断后再次启动，所有条目都迁移完整。
- **G4**：回归全部通过：
  - 全部 `scripts/test-*.mjs`
  - `npm run test:e2e`
  - `e2e-filetree`
  - `e2e-perf`（E8 不得劣化）
  - `e2e-index-visibility`
  - `e2e-files-feedback`
  - `e2e-reader-regress`
  - `git diff --check`

## 明确禁止
- 清理只匹配本应用自己的命名规则和自己的目录，不删除任何不确定归属的文件。
- 不在启动的关键路径上同步执行清理。
- 不新增依赖，不改既有断言。
- 不读写 `~/.xuewen-workbench`、`/Users/mayu/Downloads`。
